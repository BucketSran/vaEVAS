# 四后端试点的故障归因

2026-09-27。基于冻结试点 `dvs2-starter-20260927-01`，另做有界诊断 `dvs2-diagnosis-20260927`。结论针对实际安装版本和这些编码，不扩展为整个工具的能力清单。**本轮发现了仿真器实现问题，也发现了我们自己的模型语法和配置遗漏。** 未修改仿真器；诊断变体没有替换原始成绩，正式 DVS 资格仍为 `I`。

## 1. 先纠正 V6 的比较前提

原始 V6 用 `{1.0}`、`{1.0, 0.5e-6}` 表示 Laplace 系数。我们声明采用的 [Verilog-AMS LRM 2.4](https://www.accellera.org/images/downloads/standards/v-ams/VAMS-LRM-2-4.pdf) 在 §3.4.2、§4.5.11.5 使用带前导撇号的匿名数组 `'{…}`；附录 G.4 解释了这一语法变更。Spectre 接受旧写法不能代替规范核对。

因此，**原始 Gnucap V6 编译拒绝首先归于测试编码不符合选定规范，不能算作 `laplace_nd` 能力缺失。** 原始记录及 DUT 保留用于复核；[v6-lrm24.va](diagnostics/v6-lrm24.va) 是仅补两个撇号的诊断修订，尚未替换冻结案例。

| V6 基础档诊断 | 结果 | 最大观测误差 |
| --- | --- | ---: |
| Spectre，仅修正数组语法 | 满足当前观测目标 | 3.52035e-8 V |
| OpenVAF-R＋ngspice，仅修正数组语法 | 满足当前观测目标 | 3.67208e-8 V |
| EVAS，仅修正数组语法 | 仍在 lowering 失败 | 无波形 |
| Gnucap，仅修正数组语法 | 编译、运行完成，但响应错误 | 0.482948 V |
| Gnucap，在上一行基础上仅加 `short=1e-9` | 满足当前观测目标 | 3.67882e-8 V |

这几行是归因对照，不能混入原始表计算“改进后通过率”。诊断选项也不能因单卡成功直接作为正式 baseline 配置。

| Gnucap V3/V4 | 事件接受依赖严格符号乘积 `<0`，恰好落零时遗漏 | 仅加入日志的生成 C++，重现原错误并记录负→零→正过程 |
| Gnucap V6 | 原数组语法问题；修正后另受默认 `short` 对系数的截断影响 | 两步单因素对照、运行诊断和实现相互吻合 |

## 3. EVAS：四类不同的缺口

### 3.1 V3/V4：为什么更细的步长反而漏事件

先拆开原来同时变化的设置。在 V3 与 V4 C1 上分别得到：

| 步长与容差组合 | V3 | V4 C1 |
| --- | --- | --- |
| 0.1 ns 步长＋基础档数值容差 | 仍有反例 | 仍有反例 |
| 1 ns 步长＋细化档数值容差 | 满足当前观测目标 | 满足当前观测目标 |
| 原细化档，只把 DUT 的 `cross` 表达式容差从 0.2 mV 改为 0 | 满足当前观测目标 | 满足当前观测目标 |

所以不能归因于 `reltol` 变小本身。问题集中在细步长经过阈值容差带时，事件候选、历史更新与最终接受没有保持一致。

部署源码 `event.rs:157–287` 在输入尚为负、刚进入 ±0.2 mV 带时就产生候选，并更新 `last_cross_times`。`program.rs:1324–1504` 随后检查越过方向；若尚未真正过零，会丢弃候选，却没有撤销刚更新的检测历史。真正过零仍在容差带内，检测器不再发事件；离开容差带时还可能被 1 ns 的时间去重压掉。

对 V3 细化档导出的阈值附近输入，用**同一部署二进制**的检测器单独重放，得到：

| 相对真实过零时间 | 表达式值约值 | 检测器与接受条件 |
| --- | ---: | --- |
| −0.5 ns | −0.2 mV | 产生候选并登记时间；按后续方向条件会被拒绝 |
| 0 | 0 | 没有候选 |
| +0.5 ns | +0.2 mV | 再次候选所用时间距已登记时间仅约 0.9 ns，被去重 |

同一段输入将表达式容差设为 0，在过零处产生有效候选。这和两张卡的单因素电路对照一致。另保留的理想网格合成探针在容差带边界上表现略有不同，也提示浮点落点会影响这一缺陷。

**证据边界：** FFI 重放直接观测真实二进制的检测器状态；表中“后续方向条件会拒绝”由对应源码计算，并非插桩后的完整 Rust 电路内部轨迹。V4 的同类原因得到单因素对照支持，但未逐个重放其所有时钟/复位事件。把容差设为 0 是定位手段，不是已验证的通用修复。

### 3.2 V5：是语法入口缺少参数，不是运行太慢

本卡使用 `timer(start, period, time_tol)`。部署 `compiler/parser.py:1987–2003` 读完第二参数便要求右括号，于是遇到第三参数前的逗号报 `Expected RPAREN, got COMMA`。程序没有进入定时事件执行阶段。不能由此说 EVAS 所有 `timer` 都不能运行；可以明确说此版本不接收本卡的合法三参数形式。

### 3.3 V6：有滤波执行路径，但可转换的表达式形态过窄

部署 `simulator/backend.py:8278–8357` 的一阶 `laplace_nd` 收集器只接收特定模式。对于输入电压访问，只要第二节点 `node2` 非空就拒绝，所以 `V(vin,vref)` 不能进入此路径，即便网表把 `vref` 接地。

在原始 V6 上只改为等价的 `V(vin)` 后，EVAS 能执行，最大观测误差约 0.2593 mV，满足本轮 0.6 mV 目标。这个单节点对照保留了旧数组写法；另一个仅改为 LRM 数组语法的双节点对照仍报同一 `no_event_transition_ir`。这些结果与明确的源码拒绝条件一致，定位到表达式 lowering 覆盖缺口；并未证明任意输入、任意阶滤波均受支持。

### 3.4 V7：连续贡献是约束，不能靠跨时间步逐渐接近

线性卡要求每个时刻满足

\[
y=u+ky,\qquad y=\frac{u}{1-k}.
\]

A 实例初始 `u=0.2 V, k=0.5`，正确值为 0.4 V。EVAS 从 0 出发代入两次得到 0.2、0.3 V，实际初值正是 0.3 V。后续整个基础档主条件的 A/B 轨迹符合

\[
y_n=(1+k)u_n+k^2y_{n-1},
\]

A/B 最大复核残差分别为 2.22e-16 / 2.78e-17 V。这是固定做两次代入的特征，不是每个时刻把原关系解到精度要求。执行日志也同时记录了两条连续线性操作和两个 always body；部署 `expr.rs:22–85` 读现有节点值后直接写目标值。

对于非线性卡

\[
y+\lambda y^3=u,
\]

左侧导数 `1+3λy²>0`，唯一解没有歧义。但直接代入 `y←u−λy³` 的迭代导数是 `−3λy²`。当 `λ=2, y=−0.5` 时绝对值为 1.5，即该唯一解附近不满足压缩条件；简单旧值代入可能放大误差。原始初值及前几个样点与这种代入相符，但没有声称全部非线性导出点都只执行一次更新。

因此这里应提出的要求是**隐式关系必须满足残差和解误差要求，无法求解时应明确报错**，而不是“必须采用牛顿法”。源码其他路径已有最多八次的 fixed-point 刷新，不能把这次结论泛化成 EVAS 全局没有任何迭代；它并未使本卡当前路径正确。

## 4. OpenVAF-R＋ngspice：分清编译接受与语义实现

实际版本是 **OpenVAF-R v24.0.2mob＋ngspice 46**。以下不是对其他 OpenVAF 分支或版本的结论。

### V3：事件控制消失，输出恒低

V3 在两个方向的阈值事件中分别赋值 `q=1` 和 `q=0`。发布版本的 [事件 lowering](https://github.com/OpenVAF/OpenVAF-Reloaded/blob/v24.0.2mob/openvaf/hir_lower/src/stmt.rs) 对本卡这类事件直接转换事件体。实际安装编译器的 `--dump-mir` 进一步显示：状态存储值已优化成常数 0；输入 `vin` 不再是求值函数所依赖的电压输入。这样输出保持低电平是编译结果的直接后果。

### V4：事件组合在解析阶段被拒绝

[事件解析入口](https://github.com/OpenVAF/OpenVAF-Reloaded/blob/v24.0.2mob/openvaf/parser/src/grammar/stmts.rs) 在当前表达式后期待右括号，不能接收本卡的 `or` 组合。此时尚无 OSDI 模型交给 ngspice，所以不能归因于 ngspice 的时间步进。

### V5：timer 被去掉，状态翻转没有时间门控

实际 MIR 中仍有“1 减旧状态”及存储，但没有 `timer` 指定时刻的触发条件。原来应在少数离散时刻翻转的动作，变成每次模型求值都执行，可能破坏工作点迭代的一致性。原运行经过 gmin/source stepping 失败后，在 transient operating-point 阶段达到 90 s 上限，与这一机制一致。

**已确认的是 timer 时间门控丢失；超时是否还叠加其他实现问题，尚未取逐次求解轨迹排除。** 不需要再次等待 90 s 来重复已知超时，也不能把全部原因简单归为 ngspice 不支持时钟。

## 5. Gnucap＋modelgen：零点事件与滤波选项

### V3/V4：精确命中零点时，事件接受没有排入队列

原始生成 C++ 的 `cross::tr_review` 用相邻表达式值乘积严格小于零来调用 `q_accept()`。若序列是 `负数 → 0 → 正数`，两次乘积均为零；之后检测状态转为正，却没有接受事件体。

只在生成 C++ 加入日志、没有修改分支条件的对照重现了原始错误：

- V3：t=1.375 µs 输入恰好为零，下一小步为正；没有对应 accept，输出未置高。
- V4 C1：t=0.5 µs 第一次时钟过零恰为零，没有 accept；t=1.5 µs 的过零值约为 `1.78e-15`，严格符号变化成立，日志出现 `ret=1`，后续采样能发生。

这解释了“第一次采样漏掉，后面又能采样”的现象。根因在该版本生成的事件接受逻辑，不能概括为所有时钟/复位能力均不支持。V4 C0 未另外插桩，仍保留其原始波形反例。

Gnucap 网表还有数字 `0` 作为 Verilog 端口标识符的警告。独立对照把参考端改为具名 `vref` 并用 0 V 源接地，警告消失，但 V4 C1 同样漏掉首次采样，误差仍为 0.175 V。这个外壳问题需要清理，但不是该漏事件的原因。

### V6：修正语法后，默认选项改变了响应

标准数组写法使 modelgen 编译成功。接着运行日志报 `pivot too small`。对应发布版本 [Laplace 实现](https://github.com/gnucap/gnucap-modelgen-verilog/blob/20260729-dev/mgsim/d_va_laplace.cc) 在所选分母系数小于 `OPT::shortckt` 时，用此下限替换它。该运行 options 回读显示默认 `short=10µ`；本卡时间常数系数为 `0.5µ`。输出呈现约 10 µs 的响应，而非要求的 0.5 µs。

复用相同编译模型，**只加 `short=1e-9`**，警告消失，误差从约 0.483 V 降至 3.68e-8 V。再单独改为具名接地参考，数值结果保持一致。此处可以确认选项相关系数截断的因果关系；为什么该路径选到较小系数、其通用选轴策略是否还存在问题，没有进一步展开。

正式比较需要为各后端固定并公布会影响结果的有效选项；相同名称、相同数值不自动意味着相同误差控制。也不能把按此单例调通的配置立即推广到全部测试。

## 6. 证据、成本与后续边界

本轮新增 **20 个诊断探针**：16 次电路启动（含 EVAS 标准语法 V6 的执行失败）、2 次只生成 MIR 的编译探针、2 次直接调用事件检测器的 FFI 探针。总阶段调用为 16 simulate、3 compiler、1 modelgen、3 C++、2 FFI；编译与仿真属于同一探针时不重复计探针。未重跑完整 120 配置矩阵，没有新增超时。

第一次私有驱动在检查字面量时发现模型使用 `2e-4`、脚本却期待另一种写法，因断言停在下一探针启动前。修正匹配后复用已完成两条结果，原日志保留；这是驱动问题，不计为仿真器失败。

- [探针汇总及逐工件 SHA-256](diagnostics/probes.json)：20 个探针，有限观测分析与阶段状态。
- [V3 导出输入的二进制检测器重放](diagnostics/cross-wave-replay.json)及[理想网格探针](diagnostics/cross-synthetic-trace.json)：区分实际检测输出与按源码计算的后续接受条件。
- [源码来源](diagnostics/source-provenance.json)：EVAS 源码直接取自部署镜像；OpenVAF/Gnucap 发布标签用于解释，另有实际 MIR、生成 C++ 和运行日志绑定安装行为。没有伪造缺失的 EVAS build revision，也未声称完成二进制可复现构建认证。
- [私有归档收据](diagnostics/ARCHIVE_RECEIPT.json)：原始诊断源码、完整日志、波形、命令和部署 EVAS 源码归档；223 个文件及下载包 SHA-256 已核验。机器路径和原始日志不进入公开 Git。

后续应先把 V6 标准语法、Gnucap 具名参考外壳和有效数值选项纳入**新的、明确编号的实验协议**；补齐原报告列明的判定资格缺口，再冻结正式比较分母。EVAS 的事件接受、timer 参数、滤波 lowering、隐式关系求解可以分别形成最小回归和独立修复任务，但本轮未开始修复。旧版 0.8.7 结果不被新版本或诊断变体覆盖。
