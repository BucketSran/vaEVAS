# 设计目标与选题判断

我们评测模型能否用 Verilog-A 完成有实际电路意义、可以独立验收的工程工作。
交付物可以是电路行为模型，也可以是测试台中的激励、测量或检查模块。
每道题都需要严格 checker，纯代码理解和技术问答不作为任务。

当前已经确定五类工程动作。具体规格、数据包、checker、难度和题量仍需要逐题审查与实验。
这份文档说明选题依据；候选及其当前状态见[逐题工作区](../workbench/README.md)，
既有实验的资格和结果见[benchmark 入口](../README.md)。

## 以电路工作决定题目

选题先说明使用场景、信号路径，以及工程师需要保证的电路行为或性能。
通用数学问题附上电路名称不足以成立。数据建模优先考察可观测的动态，例如采样建立、
历史依赖与保持行为；是否存在这些效应，需要原电路表征确认。

电路家族与工程动作分别记录。ADC 便于解释，但覆盖还应包含 ADPLL、电源、放大器、
滤波器等适合当前范围的电路。同一电路可以支撑多个任务，不要求每个家族凑齐全部类别。

当前采用以下五类，完整的输入、交付物与验收边界见[任务定义](task-types.md)。

| 工程动作 | 核心工作 |
| --- | --- |
| 按规格构建模型 | 实现已给出的接口和电路行为要求 |
| 从数据建立模型 | 从表征记录建立能预测新实验的模型 |
| 扩展与集成 | 增加能力，或完成部件的连接与协作 |
| 诊断与修复 | 恢复故障工程应有的行为 |
| 电路测试与表征 | 建立激励、测量指标，或检出规定的违规行为 |

这些类别按本项目的 VA 工程工作划分。CVDP 的任务设计和评测方式是研究参考，
不能把数字 RTL 中某类任务的占比或难度直接套到 VA。材料与比较依据由
[研究专题](../research/README.md)维护。

## 当前采用哪些边界，为什么

| 已采用的判断 | 理由与影响 |
| --- | --- |
| 聚焦电压域行为模型 | 先建立接口和物理行为边界清楚的题目；不能由一题隐式扩大模型范围 |
| 所有题都结合独立 checker | 验收工程交付物，避免依靠文字解释、参考代码相似度或主观判断给分 |
| 合并测量与验证为电路测试与表征 | 同一个 VA 测试台可承担两者；保留测量准确性与违规检出的不同验收目标 |
| 不设置仿真加速、收敛及异常耗时题 | 本阶段聚焦电路建模与测试工作，这些方向不进入题目计划或修复子类 |
| 允许共享电路资产，保留同源关联 | 多种工作可以发生在同一电路上；统计不能把相关题目当成完全独立的能力证据 |
| 不按文件数、代码长度或预估难度加权 | 工程规模不直接代表完成质量；完整仓库任务可以单列分析 |
| 优先审查旧 benchmark 资产 | 复用已有材料，但重新核对规格、来源和 checker，不继承旧认证为当前验收 |

[电压域行为模型](../../GLOSSARY.md#电压域行为模型)限制候选需要建立的行为。
验收环境可以包含由后端求解的晶体管和其他器件；要求候选实现端口电流、输出阻抗及
负载耦合的任务暂不纳入当前范围。出现足够的范围外工程需求后再讨论扩展。

规格建模既可要求功能级理想行为，也可要求指定动态或非理想行为，按工程用途选择。
如果试跑表明功能级题过于简单，再调整后续建设重点，不能事先把所有理想模型都判为无价值。

## 用三个例子讨论题目是否成立

以下是用于讨论的代表方向，没有给出已冻结的数值或已通过校准的声明。

| 方向 | 给定材料与交付物 | 独立验收思路 | 最需要同行判断 |
| --- | --- | --- | --- |
| Alexander BBPD 单模块 | 给出接口、内部三点采样与历史对齐要求，交付完整 VA 判相模块 | 从数据和时钟输入独立重建样本组，检查方向、启动有效性和输出时序 | 理想采样与重合边沿规则怎样定义才合理？允许哪些实现差异？ |
| 真实采样级数据建模 | 给出输入、时钟、前置历史、工况及表征记录，交付同接口 VA 模型 | 用留出的完整实验比较波形、采样误差和公开指标 | 哪些动态确实存在？公开实验是否足以辨识它们？ |
| POR 测试与检查 | 给出可读 DUT、接口和电源复位要求，交付 VA 激励与监测模块 | 独立检查实际施加的条件、测量值、误报、漏报及报告时机 | 哪些电源轨迹与复位性质最重要？延迟应从哪个事件计起？ |

系统任务另有一个必须回答的问题：模块是否真正参与规定的系统行为？例如补齐 SAR ADC
比较器或 SAR 逻辑，应检查指定职责、接口和协作。仅把外部模拟输入直接量化为数字码，
即使最终输出接近，也不能证明完成了要求保留内部架构的系统任务。

请教同行时，优先形成以下结论：

1. 工作在真实工程中何时发生，是否值得保留为任务。
2. 最小模型需要哪些状态、动态和端口作用，哪些效应可在明确条件下忽略。
3. 给出的规格、数据或工程是否足以完成任务，是否存在隐含要求。
4. 哪些独立观测能区分正确实现、典型错误和绕过工程目标的实现。
5. 工作单元是否适当；难度先作假设，再用模型试跑检验。

## 上下文、来源与题数分别记录

三个上下文层次均保留：单个工作单元、有边界的小工程、完整仓库任务。
首轮完整仓库任务较少，具体数量在代表题研究后确定。提供多个文件不自动构成系统任务，
要求修改多个文件也不自动形成更高难度。

任务来源允许真实工程问题、合理人工故障和依据明确工程需求原创的任务。
每题标明来源、实际用途、正确行为和验收依据；人工错误还需解释发生机制。
来源与分发遵循[使用约定](../reference/README.md#使用约定)。

旧 DUT、Testbench、Bugfix 是候选来源，不要求成套迁移。
普通参数变化作为测试条件，不增加题数；新增工程要求是否构成新任务需单独说明。
报告同时给出任务数、来源分组与工程工作覆盖，最终汇总口径仍待确定。
旧七类各 5–10 题的配额不再是当前建设目标，历史资产和成绩保留原身份。

## 先确认工程价值，再确认难度

保留少量容易但重要的基础任务，核心挑战题需要在合理交互预算下仍有区分度。
一次失败、代码长或参数多都不足以证明困难。
首次提交出错后立即根据反馈修好，可以分析过程，但不能单凭这一点认定为挑战题。

建设顺序是明确工程场景，定义交付物和公开合同，校准参考解及典型错误，
再用多个模型试跑，区分任务缺陷、环境问题和模型能力不足，最后冻结合格版本。
校准与评测细则见[评测原则](evaluation.md)。
