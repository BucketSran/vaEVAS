# 题包格式与验收约定

本页是题包结构与交付合同的详细参考。人工 review 看[关键原则](design.md)，
Agent 的执行要求与完成条件见[英文流程](agent-workflow.md)。

本 benchmark 评估模型与智能体能否用 Verilog-A 完成电路工程任务。
任务采用 Harbor 格式，交付物由经过作者校准的独立 checker 验收。
纯代码理解和技术问答不作为任务。

本文保留此前已确认的题包分工。目录录取规则与当前状态见
[benchmark 入口](../../../README.md)。正式题仅在 `benchmark/tasks/`；当前草稿在 `material/draftbench/batches/<batch-id>/tasks/`，早期题包在 `material/historyref/tasks/`。
下方关于 `SOURCE.md`、参考解、checker 和结果记录的要求用于完成题包，草稿不因此自动录取。

## 设计与评测约定

- [设计目标与选题判断](design.md)：工程价值、电压域范围、上下文层次和来源。
- [五类任务定义](task-types.md)：输入、交付物、修改权限与独立验收。
- [评测与复现原则](evaluation.md)：Agentic 与 One-shot、固定后端、作者校准、环境缺陷与成绩报告。

电路功能和五类工程动作通过总览与任务元数据关联。共享电路不因派生出多个任务而失去同源关系。
设计认可、作者校准、运行适配和正式发布分别记录；合入 main 不自动代表所有后端均可复现。

## 任务结构

### 单文件题的目标规范

2026-10-14 题包规范讨论已确认，采用 analog-design-bench 的原位编辑与交付方式：
仓库中的 `environment/starter/circuit.va` 进入环境后成为 `/app/circuit.va`。
该文件提供固定接口和起始内容，求解者直接编辑它，最终也收集同一文件。
`task.toml` 明确声明 `artifacts = ["/app/circuit.va"]`。多文件工程见下方[交付约定](#多文件工程的交付约定)。

英文 instruction 开头简述本题工程工作，以 `Spec`、`Deliverable` 两个主段组织。
`Spec` 说明行为、合法工作范围与验收尺度；`Deliverable` 用条目说明工程交付要求，再给出公开测试入口。
短题不另设 `Constraints` 或 `Operating conditions and acceptance` 小节，按下方职责组织内容。
模块与端口声明仍在起始文件中，题面引用接口和端口顺序要求，不重抄完整声明。

| 内容位置 | 应回答的问题与边界 |
| --- | --- |
| `Spec` | 做到什么行为、参数如何定义、在哪些输入与时序范围内满足什么验收尺度。影响正确性的误差界限、采样时刻和事件排除范围留在这里；终评范围与评分用短句说明 |
| `Deliverable` | 逐项说明编辑路径与接口、所需工程实现、必要模型约束和实际提交限制。行为定义的题明确接受满足接口与外部行为的不同实现，不规定状态变量或事件组织；已有工程的组件职责仍须保留 |
| 公开台架说明 | 观测点的具体生成方法、台架运行方法、后端版本、超时、输出位置与诊断。这里可以说明如何测量，但不能暗中新增题面未声明的行为或门槛 |
| 作者记录 | 来源论证、gold 组织方式、校准过程和待定证据，保留在 SOURCE 与现有结果记录，不搬进 solver instruction |

Deliverable 的条目之后只写真实可用的公开命令与说明链接，不杜撰独立 preflight 工具。
限制必须有明确对象，例如禁止外部文件/进程访问的是提交的 VA 模型，不能误写成禁止 agent
读取公开材料或运行测试程序。固定尾段已说明的通用执行要求不再另加一套。
将测量细节移出题面时，须在既有公开台架说明中保留并验证链接；不能仅删除，也不能指向作者私有文件。
不要用固定字数、关键词数量或机械删段落代替上述内容判断。

instruction 保留 Agent 环境中的路径：绝对路径以 `/app/` 为根，题面中的相对材料路径也按 `/app` 解析。
中文人工 review 使用仓库相对链接，直接链接题面、starter 与公开台架说明；不要为了仓库点击方便而改坏 Agent 路径。
两类链接分别核验。现有 lint 检查题面与公开材料，并在题包 README 存在时按仓库布局检查其链接；
放在功能族或批次页的人工入口仍须核对。不要求另建一份人工文档。

### 行为说明的详细程度与草稿边界

行为说明以“求解者能确定什么输出算正确”为准。每项验收要求应能对应公开规格中的明确条款，
或由已写出的规则无歧义地推出。复位、初态、重新触发与取消等工程约定不能仅靠模块名称推断。
合并可推导的重复场景，保留独立条件；可用优先级规则、状态表或输入序列表达，不以条目数判断是否过细。

说明行为不等于指定实现。行为定义的 VA 题保留输入、输出、事件参考与边界，接受等价实现；
只有工程动作本身要求某种组件职责或内部结构时才限定它。外部数据集有的题只写可测电气表现，
有的还规定算法、状态机和文件组织，不能据此一律删减或增加实现要求。
比较描述完整性时，应包括题面实际提供并引用的公开规格；作者私有材料不能补足求解者缺失的合同。
具体样例见[AnalogBench 与 CVDP 核对](../sources/timing-contract-comparison.md)。

起草前按[规格提取流程](agent-workflow.md#extract-and-review-a-behavior-agreement)核对来源角色。
从 checker 恢复的测试点、gold 的内部结构和故障 baseline 的现状均须保留证据身份，不能直接写成
普遍要求。先说明可观察行为，再说明适用条件与验收尺度；测量公式、参考值、窗口和量词应明确。
“整个保持区间的最大偏差”与“两个时刻之差”是不同要求，“各工况下所有代码”与“仅标称工况的
代码扫描”也不同。具体验证网格可放公开台架说明，既定行为范围仍留在公开合同。
作者意图、数值取舍与尚待确认的冲突留在 SOURCE；规范依赖须随公开材料可得并标明版本。
[30 题重建研究](../research/spec-extraction-study.md)提供了区分这些情形的证据和写法。

早期题面保留一处简短草稿标识，在相关条件处用具名 `TBD` 标明未定数值或规则，保留其适用对象与已知参考。
待定原因、人工讨论、旧 checker 的差距、修复计划和历史成绩写入 SOURCE 与现有人审记录。
公开台架尚使用临时尺度时，使用说明应明确反馈仅针对该提案；题面给出真实入口即可，不重复开发进度。
不得为缩短题面删除已确定的行为，也不得将待定项静默变成不限范围或已通过验收。
这些内容判断由作者逐项复核，现有 lint 负责结构、材料与阶段检查，不用关键词或字数上限代替。

### 时序边界与验收说明

事件型题目按实际需要说明下列边界，短题可合并成几句。数值尚无依据时保留待定，不能照抄外部题目的数字。
[AnalogBench 与 CVDP 样例核对](../sources/timing-contract-comparison.md)说明来源事实与可借鉴的写法。

| 要说明的内容 | 核对重点 |
| --- | --- |
| 输入变化 | 初始电平、输入斜坡的起止定义、有效窗口与事件间距；明确间距按哪个阈值穿越或时钟边沿计算。相邻事件间距不自动约束第一次事件距起点、最后一次事件距终点的距离 |
| 输出响应 | 理想瞬时行为还是允许有限延迟、过渡或建立过程；若需要有限过渡，定义可观察响应及时间尺度，不强制使用 `transition()` 或某种事件写法 |
| 计时与误差参考 | 区分行为发生时刻、预期采样值的参考时刻、实际观察时刻和允许误差；探针偏移或排除窗口不能暗中成为允许的采样延迟 |
| 起止与相邻事件 | 初态、复位释放、启动等待、观察窗口终点；事件靠近起止点、两个实例事件靠近或同刻时，明确规则的适用对象和优先关系 |
| 评分窗口 | 哪些时刻或区间必须检查、哪些暂不检查，以及排除边界是否包含端点。不能先按排除规则删去必检点，再把其缺失记作提交失败 |

不要把输入斜坡时间、模型输出过渡时间、仿真分辨率和 checker 观察间隔写成同一个概念。
输入斜坡有限也不能保证阈值穿越远离观察窗口边界，参数变化须一起考虑。
当零时刻必须检查时，应明确它与事件邻域排除的关系；若采用启动等待或限制事件距窗口边界的间隔，
须先有工程依据并在公开合同声明，不能只在隐藏台架中追加条件。

作者从允许范围构造至少一个起点/终点附近或最短窗口的手算例，沿“合法输入、事件时刻、观察点、判定”核对是否自洽。
公开与终评采用同一合同；具体网格生成留在公开台架说明。待定项、依据和待执行校准留在 SOURCE。
这些检查不要求在未授权时运行模型实验；进入校准时再验证受影响的正确替代实现和典型错误。

文件名统一为 `circuit.va`，内部顶层模块使用电路功能名，例如 `track_hold`、
`interleaved_sampler`；新题不额外拼入题号前缀。改编已有真实工程时保留其原模块名和接口。

2026-10-19 人工 review 确认以下起始材料分工：

- 从规格新建模型：starter 只提供必要的 include、模块与端口声明和 TODO。参数名、含义、类型、默认值与合法范围写在 `Spec`，由求解者完成参数声明和行为实现。
- 修改已有模型：提供完整的原始 Verilog-A 代码及必要依赖。扩展题提供正常工程，修复题提供待修复的完整工程，保留已有实现。
- 兼容既有电路：在题面规定替换边界、模块名、端口及实际连接与调用要求。若调用依赖特定参数名或默认值，按实际依赖列出要求；兼容要求本身不决定是否提供参数声明，起始代码仍按新建或修改任务提供。

新建模型的 starter 不预置内部节点、状态变量或算法，默认不添加逐端口说明。
只有浮动参考域、含义不直观的引脚等特殊接口关系才补短注释。
外部格式参照见[analogbench starter 核对](../sources/analog-task-package.md)。

`testbench/` 提供可运行的公开测试和分析入口，输出指标与公开条件的 PASS/FAIL。
按任务需要提供仿真台架和分析入口。短题在 instruction 中给一条运行命令即可；
多台架、特殊连接或输出解释较复杂时，增加英文 README，说明运行方法、公开覆盖和输出含义，
不重复完整 `Spec`。
公开反馈判断候选在该公开用例中是否满足任务要求，不等同于整题通过；
测量题判断的是测量与报告是否正确，不把被测电路本身性能合格作为仪器通过的前提。
终评使用独立条件，参考解与终评材料继续与求解环境隔离。

`tests/test.sh` 是评分入口，`tests/verify.py` 执行或调用独立验收与评分。
仿真台架按需放入 `tests/benches/`，参数用例、辅助代码和 verifier Dockerfile 按实际需要添加。
作者准备的[校准样本](../../../../GLOSSARY.md#校准样本)按需放入 `tests/fixtures/`，
不强求每题准备相同数量的样本。作者校准工具把样本逐个作为候选交给同一 checker，
验证正确实现被接受、指定错误被识别；样本应关联预期结论和所检要求，运行异常另记。
正式终评只评分求解者提交，不将这些样本计入该次成绩或 benchmark 题量。

参考解按人工 review 需要注释关键电路机制、状态保持和边界处理，不要求逐行注释；
简单实现可以没有额外说明。建模 starter 的最小注释规则不限制参考解。

当前开发阶段保留 `SOURCE.md`，作为作者与 reviewer 查看来源、改编及同源关系的入口，
链接已有草稿工作区材料。它是本项目的作者记录，不是 Harbor 要求，也不进入求解环境。来源、建模选择和待定项的分节，以及 `task.toml` 的少量声明，见[阶段静态检查](evaluation.md#题包静态检查)。

完成真实运行后，在 `results/reference.json` 保存参考解的指标、结论与版本身份，
在 `results/calibration.json` 保存独立 checker 的正确与错误对照校准摘要。
原始波形和大日志留在已有运行记录中；这些 JSON 是作者证据，不作为候选的期望答案，
也不进入求解环境。合同或制品变化后，保留结果所对应的版本，不能把旧运行改记为新版本证据。

结果表使用 `Specification | Limit | Value | Pass/Fail`，从与 JSON 相同的结构化判定结果生成，
完整展示验收条件。先讨论行为与依据，再建立 gold、完善台架与评分，最后按授权校准；
具体规则见[验收方案与结果呈现](evaluation.md#验收方案与结果呈现)。

单个可修改文件的题包采用以下目标结构。`environment/starter/` 的公开材料进入 `/app/`，
参考解和独立终评材料留在求解环境之外；下列结构不要求短规格额外拆文件。

```text
benchmark/tasks/<task-id>/
├── instruction.md
├── task.toml
├── SOURCE.md
├── environment/
│   ├── Dockerfile
│   └── starter/
│       ├── circuit.va
│       └── testbench/          # 公开台架与分析入口，README 按需
├── solution/
│   ├── circuit.va
│   └── solve.sh
├── tests/
│   ├── test.sh
│   ├── verify.py
│   ├── benches/               # 按需
│   └── fixtures/              # 按需，作者校准样本
└── results/
    ├── reference.json
    └── calibration.json
```

上述是已确认的目标规范。56 个保留题包仍使用原工程合同；当前 R01 批次有 ideal 实现与有限采集合同草稿。
ideal 已接入公开自测和独立终评，作者校准仍受后端缺口阻碍，状态见[该题入口](../batches/r01-sampling-01/tasks/r01-spec-ideal/README.md)。题包生成器和实际题包仍需按规范适配；[阶段静态检查](evaluation.md#题包静态检查)已接入，完整运行适配另行验证。
目录搬迁或旧格式检查通过不能作为已与 analogbench 统一的证据；
完成实际转换和受影响的校准前，历史结果继续按原运行合同解释。
已读取的格式参照为 [analogbench MUX 题包](https://github.com/Arcadia-1/analog-design-bench/tree/972f7cd7c95381134387b250edf18f3bd23bdd25/tasks/sky130-analog-input-mux-8to1-pvt)。

### 固定执行尾段与参考材料

2026-10-19 确认：当前单文件题使用 [INSTRUCTION 模板](../templates/INSTRUCTION.md) 中
`BEGIN/END VABENCH EXECUTION FOOTER` 标记之间的两段英文作为固定尾段。
只复制标记之间的正文到题面末尾，不复制两条 HTML 标记；模板占位提示也不能进入最终题面。
题目特有的规格、交付路径和公开运行命令放在它之前。
正文沿用 AnalogBench 的执行要求，仅删除要求优先查阅参考指南与 starter 示例的那一句。
尾段保留材料边界、有限浏览、及时建立可运行候选、问题调查、迭代和文件采集约定。
模板是唯一维护来源；现有 lint 从模板读取并核对单文件题，允许空白与换行变化，不允许删改、重复或残留作者标记。
多文件或目录交付继续按下节规定明确采集对象，不机械套用单文件尾段，也不在本轮扩展模板变体。
旧格式保留题不因此追溯改写。

当前规格重建题不额外附送通用 Verilog-A 语法指南或模型示例集。
最小 starter、完整行为规格、验收条件、公开台架及必要的环境运行说明仍须提供。
修改已有模型的题仍提供完整原始代码和依赖；任务本身需要的数据和工程材料也不省略。
不附指南不等于闭卷，联网和工具权限由实际环境另行规定。后端运行缺口不记作候选建模失败。
尾段中的超时采集与空文件零分是执行合同，需在运行验收时验证；文字一致不代表运行机制已经兑现。

### 多文件工程的交付约定

2026-10-15 已确认：沿用 Harbor 外层结构，在 `/app/` 原位修改并自动收集交付物。
默认逐文件声明，确有自由拆分模块或维护工程目录的需要时，才开放指定目录。
输入是多文件工程，不代表交付也必须有多个文件；例如在完整系统中补一个模块，可以只交付该模块。

`environment/starter/` 按相对路径复制到 `/app/`。新建 VA 工程可使用下列布局，
少量文件可以平铺，子目录按需增加；改编真实工程时保留原文件名、目录和入口，不强制改名为 `circuit.va`。

```text
environment/starter/
├── circuit.va             # 新建 VA 工程的顶层入口
├── modules/               # 按需拆分模块
│   ├── sampler.va
│   └── controller.va
├── design_params.inc      # 需要独立参数文件时才提供
└── testbench/              # 公开测试与分析入口
```

模块与端口声明留在对应起始源码中。建模、扩展和修复的起始内容继续按上方分工提供。
工程入口、依赖或运行方法较复杂时，增加英文 README，避免把完整规格另抄一份。
`solution/` 按相同相对路径保存参考交付文件，由 `solve.sh` 安装到 `/app/` 对应位置；
固定依赖由环境提供。`tests/`、`SOURCE.md` 和 `results/` 的职责与单文件题相同。

英文 instruction 仍用 `Spec` 与 `Deliverable`。`Deliverable` 明确交付路径和可修改范围，
必要的接口或架构限制放在 `Spec` 的 `Constraints` 中。文件与模块名采用工程本身的名称。

| 内容 | 修改与交付约定 |
| --- | --- |
| 待完成或修改的模块 | 逐文件列出；允许整体重写，仍须满足规定的接口、行为和模块职责 |
| 系统连接、设计参数、源文件清单 | 按工程工作决定是否可改，明确列入范围；文件可见不代表可修改 |
| 固定依赖、官方公开测试、评分材料 | 保持作者版本，不作为求解者可修改的交付物 |
| 新增辅助模块 | 仅在题目明确开放的目录中新增，说明如何被工程加载并纳入交付 |
| 自定义实验文件 | 按题允许用于自测，是否属于交付物另行声明 |

当任务是开发 VA 测试或测量模块时，该模块属于可修改的交付物；用来验收它的外部测试保持固定。
不能仅凭文件名或目录名含有 testbench 就把它视为固定材料。

`task.toml` 的 `artifacts` 与公开交付范围保持一致。指定文件交付时，列出每个完整路径，
例如 `/app/circuit.va` 与 `/app/modules/sampler.va`。开放目录时，声明目录路径，
并说明允许新增、删除和重命名哪些文件，以及必须保留的入口与接口。
目录中含有固定材料时，须将其与可交付部分区分，不能因收集目录而允许覆盖固定材料。
交付源码所需的新依赖也必须处于声明的收集范围内。

求解者保存工作文件即可，不要求 Git 提交、打包或手写 patch。结束时收集声明范围的当前内容，
包括允许的新文件，不以是否执行 `git add` 判断；未声明的临时实验、波形和缓存不作为交付物。
运行器可生成差分供 review，但差分不能替代实际交付文件。

终评在独立环境中恢复固定工程基线，再装入声明的交付物。开放目录交付时，
需要保留合同允许的删除与重命名结果，不能让单纯覆盖复制把已删除的文件恢复回来。
固定材料不得被候选覆盖，收集遗漏应与候选本身缺少依赖分别诊断。
这些是运行适配的要求，当前文档更新不表示收集、恢复或完整 Harbor 流程已经验证。

来源分工见 [analogbench 题包核对](../sources/analog-task-package.md#多文件约定讨论的补查2026-10-15)
和 [CVDP heavy 多文件核对](../sources/cvdp-heavy-multifile.md)。
[Harbor artifacts](https://docs.harborframework.com/tasks/artifacts)支持文件或目录收集，
[独立 verifier](https://docs.harborframework.com/tasks/separate-verifier)支持重新建立评分环境。
默认逐文件声明、修改权限与目录恢复要求是本项目确认的约定，不是对所有 CVDP heavy 题目的描述。

### 作者目录与记录

新题的 `instruction.md` 用英文说明工程起点、行为要求、可修改范围与交付。公开起始工程按[目标规范](#单文件题的目标规范)提供，题面引用其中已有的声明，明确仍需实现的要求。短行为规格可以直接放在题面；已有工程规格可以引用，内容长或需要共用时再拆文件。`task.toml` 配置任务，`SOURCE.md` 记录来源与改编。
`environment/` 提供运行环境与公开输入，`solution/` 保存参考解，`tests/` 执行独立评分，`results/` 保存版本对应的作者运行摘要。
评分按 Harbor 约定输出 `/logs/verifier/reward.txt` 或 `reward.json`，详见
[Harbor 任务格式](https://docs.harborframework.com/tasks/overview)。
从功能族讨论到题包交付的顺序见[建设流程](evaluation.md#建设流程与完成标准)，
英文起草模板与样板核对见[题包建设](../templates/README.md#从方向转成正式题包)。
正式题集的 `benchmark.toml` 与 `defaults.toml` 放在 `benchmark/tasks/` 根下；
旧七类清单归入历史区，其原身份见[路径对照](../history/README.md#首批题集配置的位置)。

## 维护与历史

开发中发现的可复用问题进入[候选登记](../CANDIDATES.md)，先记录触发条件、独立预期与证据，
不自动创建题目或增加评分分母。`python3 -B scripts/benchmark_workbench.py --check` 检查历史题卡、
现有 `vN-*`（N ≥ 2）任务登记与生成索引，并对新题包执行[阶段静态检查](evaluation.md#题包静态检查)；通过不证明完整运行、校准或人工认可。
共享 checker 的副本同步、校准与环境说明见[评分实现](evaluation.md#共享评分程序)。

[历史题集与建设记录](../history/README.md)保留初筛、旧七类和后续两批的来源及实验入口；
[历史设计稿](../examples/README.md)保留早期设想，包括已不属于当前五类的方向。
