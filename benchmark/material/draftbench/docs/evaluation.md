# 评测与复现原则

本页是评测与运行的详细参考。人工先看[审核原则](design.md)和具体电路组的简短结论，
Agent 按[英文流程](agent-workflow.md)执行；本页保存阶段、判据和证据的完整定义。

公开规格与独立判据定义正确性，仿真后端执行验收所需的实验。
所有工程类别都配备严格 checker；编译成功、某个仿真器的输出或参考源码相似度
不能直接作为正确答案。任务格式与当前执行入口见[benchmark 说明](task-package.md#任务结构)。

本文的 golden TB 指作者维护的评分台架、实验实例和判定程序，gold 指参考实现。
Spec 定义正确性，golden TB 验证这些要求；评分测试不得增加隐藏要求，也不因名为 golden 就证明覆盖完整。

## 建设流程与完成标准

每个电路功能族按当前授权向前推进，讨论一类后可以将该类转成任务，不必等全部类别讨论完。
继续工作时先从功能族 README 和现有 issue、PR 或交接中找回当前阶段、已认可范围、
未完成交付与下一项依赖。已有授权继续有效，不为每道题增加人工审批。

建设顺序为：固定题包范式与自动检查，明确有来源的应用和初步行为要求，建立有依据的 gold，
再设计公开自测、终评与评分，完善英文 instruction。各步可因新证据回查，不要求一次写定。
早期先约定要观察的行为与典型错误，数值范围、容差和运行证据允许待定。

| 阶段 | 完成依据 | 可复核产物 |
| --- | --- | --- |
| 功能族与初步验收讨论 | 真实应用、已有代码、论文或其他资料说明用途；短行为约定区分来源支持、建模选择和待定项 | 电路价值、给定材料、求解者工作、同源区别；不要求评分数字或完整 instruction |
| gold 资产建设 | 关键行为可追溯到来源或明确的建模选择；保留原件与改编关系，gold 是待核验参考实现 | 源码、依据与未知项；已有运行不自动证明新题成立 |
| 验收设计与题面完善 | 从行为约定和 gold 设计激励、观测及错误对照，公开与终评遵守相同规则；instruction 准确描述实际交付和公开材料 | 要求、依据、公开测试、终评、典型错误的对应关系；数值待校准时明确记录 |
| 作者校准 | 在获准执行后核对 gold、其他正确实现和典型错误，固定有依据的评分数值，走通题包执行 | 实际通过与失败、环境缺口、版本及证据；不以 gold 输出作为唯一真值 |
| 批量建设与最终题目 review | 代表题成立后复用范式和环境，逐题核对工程价值、覆盖和必要校准 | 完整题包及差异；格式通过不替代人工认可 |
| 模型实验或发布 | 仅按相应授权推进，固定材料、后端、预算及版本 | 模型成绩、发布资格与实际 Git 集成状态 |

2026-10-19 本轮调整了建设顺序，保留此前将人工讨论前移的决定。行为约定先于 gold，
完整 instruction 随资产和验收设计完善；不要求提前冻结数值，也不新增逐阶段审批。
gold 所需工作参数与评分容差分开记录，前者也需来源或明确的建模选择。

各阶段产物由 Agent 准备并自查；人工参与点见[审核分工](#人工介入与批量交付)，不要求人在每阶段逐题签字。
批量生成设计草稿可以保留数值与运行待定。批量交付可评分题包前，先走通已确认代表题的完整样板，
包括公开试跑、参考交付和独立终评，并核对其他正确实现与典型错误的校准。
若环境已经验证，复用其工具链和隔离方案，验证新题实际接入即可；遇到跨仓库依赖，
先用样板确认依赖可用，再扩大运行。样板的人工审核范围由本轮要求决定，不要求逐题冻结。
格式样板与电路内容样板可能不同：复用目录和运行入口，不照搬另一题的行为或数值。
需要首轮模型实测来决定后续难度时，按当前批次安排完成该项依赖；作者校准不能代替模型解题结果。

完整题包中的文件分工以 [benchmark 任务结构](task-package.md#任务结构)为准。
英文题面的起草模板见 [INSTRUCTION.md](../templates/INSTRUCTION.md)，模板占位需换成本题要求或明确的待定说明；早期不要求填写未知数字。
接口文件由公开合同编写；从参考解裁掉实现体不能替代接口设计。
短行为规格可以放在 instruction 中，长规格或已有工程文档按需引用，不强制拆分。

作者先从求解者看到的材料核对合同，再校准 checker。事件型任务需明确开始、完成、中断、
复位、结束时的行为，记录身份与顺序、误差参考和合法实验范围。数值容差应配合输入变化、
事件间距与后端精度；相同身份的允许实现差异应被接受。checker 不能只接受作者选择的代码或输出顺序。
这些内容按实际任务需要填写，不把全套记录协议强加给基础题。

`benchmark_workbench.py --check` 在登记、索引和正式清单检查之外，按建设阶段检查新题包，
详见下方[题包静态检查](#题包静态检查)。旧批次的登记检查继续保留，并单独报告；
R01 的旧路径检查已归档，不作为新规范的验证。
工程价值、规格是否充分和可读性由 reviewer 判断。格式检查、作者校准、人工设计认可、
模型实验和 Git 集成分别记录。CI 接线只表示检查已配置；实际执行结果需要单独报告。

合同变化后重做受影响的校准。只改排版或移动接口说明时，核对行为、候选、台架和 checker
是否变化，并保留运行时题面身份，不能把历史证据改写成新版本的执行记录。

### 题包静态检查

从仓库根运行 `python3 -B scripts/benchmark_workbench.py --check`。该命令只读，
同时检查批次登记、生成索引和新题包；`--write` 仅更新生成视图，不改题面、源码、阶段或审核状态。
检查单题或提前核对下一阶段材料时，使用同一个入口：

```sh
python3 -B scripts/benchmark_workbench.py --check --package <task-directory>
python3 -B scripts/benchmark_workbench.py --check --package <task-directory> --stage implementation
```

检查层级沿用现有 `metadata.stage`，不另设一份题目状态。`--stage` 可选择下表检查层级，
但不能降低题包已声明阶段或正式目录所要求的检查。阶段检查失败表示材料尚未满足该阶段的静态要求，
不等于候选解题失败；草稿仍可保留并继续建设。

| 检查层级 | 默认选择依据 | 累加检查内容 |
| --- | --- | --- |
| `contract` | `source-screening`、`design-draft`、`deferred` | 初步题面、分节来源记录、路线与待定声明、按动作提供的 starter；`Spec` 与 `Deliverable` 主段；单文件题使用固定执行尾段；交付路径在声明与 Deliverable 中均出现；路径存在且不重叠；公开本地链接和字面量 include 不越出公开工程 |
| `implementation` | `implementation` | 行为依据已记录且有引用；Dockerfile、公开 testbench 及题面的使用入口；参考文件按交付路径对应；`solve.sh`、`test.sh` 与 `verify.py` 存在且非空 |
| `calibration` | `calibration`、`frozen`、`model-trials` | 无已声明待定项；两份作者结果文件可解析为非空 JSON 对象，拒绝重复键和非有限数值 |
| `accepted` | 正式 `benchmark/tasks/`，或显式预检 | 上述材料齐备，`review_status = "accepted"`，SOURCE 中有正文审核记录或审核记录链接；正式清单的目录、ID、顺序与默认配置入口一致 |

新题只在现有 `task.toml` 增加以下声明，不新增流程文件或状态机：

| `metadata` 字段 | 约定与检查 |
| --- | --- |
| `circuit_route` | `all-va` 或 `device-circuit`。后者包括来源于真实电路的固定数据任务，不能用后端名代替路线 |
| `starter_kind` | 可修改 VA 文件采用 `new-model` 或 `existing-model`；规格/数据建模采用前者，诊断修复采用后者。没有可修改 VA 的测试程序题不要求该字段 |
| `pending` | 显式列出尚未完成的 `basis`、`grading`、`runtime`，没有已知待定项时用 `[]`。原因与下一项缺口写在 SOURCE 的待定项，不复制数字或证据 |

`SOURCE.md` 用“行为依据 / 建模选择 / 待定项”三个非空二级段落分别记录事实、选择和未知，
也接受英文 `Behavior basis / Modeling choices / Open items`。已有来源、改编及历史记录放入对应段落，保持唯一来源。
`basis` 待定时允许尚无来源链接；声明依据已记录后，行为依据段必须含引用，本地文件引用必须可解析。
`implementation` 要求先补齐依据记录，仍允许评分和运行待定；进入 `calibration` 才要求全部已声明待定项解决及结果文件齐备。
草稿可保存候选 gold、部分 checker 和明确的待定文字，不因此自动升级。不能删除待定声明、编造数字或生成成功回执来消除检查错误。

新建 VA starter 的检查只接受简单电气模块接口、标准 include、端口声明和注释，拒绝参数、内部节点、状态及行为。
检查范围是声明可修改的 VA 文件；公开固定模型和台架不受骨架限制。已有模型的检查拒绝全包只有接口、参数或空 analog 的明显占位，
允许原参数和实现保留；实际源码完整性、复杂接口和依赖语义仍需审核及编译。该检查约束出题者材料，不限制求解者实现语法。

未到下一阶段时不要求后续文件。进入校准阶段后，结果尚未产生会报告缺少结果，不能生成占位成功记录来消除错误。
旧题身份取自保留的 v2 来源映射和 v3 五条建设路线的计划、manifest，并与 `tasks.json` 取交集；
兼容范围不会仅因登记新增 v2/v3 前缀的题号而扩大。这些旧题包在尚无 `metadata.stage`、`artifacts` 和 `environment/starter/` 时，
保留原登记检查，并明确报告为 `legacy registration only`。这不表示新格式通过，也不能进入正式题集。
新题采用新批次并声明阶段；旧题迁移时进入同一套阶段检查。历史区不按新题包规范追溯改写。

静态检查只解析本项目使用的 TOML 字段，不替代 Harbor 实际版本的完整配置预检。
单文件题的[固定尾段](task-package.md#固定执行尾段与参考材料)从现有模板读取，只忽略空白和换行差异；
检查要求完整尾段出现在正文末尾且不重复，注释或代码块中的副本不能代替正文；
题面若残留模板的 BEGIN/END 作者标记会报错，即使 Markdown 渲染会隐藏它们。
英文检查识别汉字和独立行、列表项中的模板占位残留，不判断英文质量；链接检查覆盖行内文件链接，
题面链接按 Agent 的 `/app` 布局解析，题包 README 若存在则按仓库布局检查链接。
人工导读应提供题面、starter 和公开说明的仓库链接；lint 不强制新建 README，也不证明链接内容足够。
不联网核验远端记录，也不核验 Markdown 锚点。include 检查覆盖公开源码的字面量本地路径，
标准 VA 头文件、变量展开和 PDK 系统路径由运行环境验证。源码接口的语义一致性仍需编译、运行和审查。

交付路径出现在题面中，并不证明修改权限已经表述充分。开放目录中的固定文件、允许删除的文件、
新增依赖及工程入口仍按[多文件约定](task-package.md#多文件工程的交付约定)审查。
Spec、Deliverable 与公开台架说明的[内容分工](task-package.md#单文件题的目标规范)、实现自由是否明确、
限制对象是否准确仍需内容 review；不以关键词命中或格式检查代替这些判断。
[时序边界检查](task-package.md#时序边界与验收说明)须核对合法输入与观察/完整性规则是否相容，
尤其是初态、最短窗口和事件靠近起止点的情况；静态 lint 不证明数值合同或 checker 正确。
静态检查不执行 Dockerfile 或脚本，不证明公开命令输出指标与 PASS/FAIL，也不证明环境隔离或目录收集正确。
这些要求需要经过实际构建、参考交付、候选收集和独立终评来验证。

来源分节与待定声明通过不代表引用支持模型，也不能证明实际编写顺序。
结果 JSON 的结构通过不代表版本身份正确或真实运行成功。审核记录的存在也不证明人已认可当前版本。
最终 review 仍核对运行版本、台架与判据、校准样本的代表性，以及工程价值和同源区别。
这些限制同时出现在命令输出中，不能用静态通过替代作者校准或人工录取。

### 验收方案与结果呈现

初步验收先记录行为和错误类型；有依据的 gold 建立后，再完善公开自测、终评、测量和评分。
逐题设计按[英文流程](agent-workflow.md#design-public-checks-and-final-evaluation)执行，
所需内容见下方约定。设计 review、checker 实现和作者校准分别记录，不能相互替代。

#### 逐题 checker 与终评设计

方案保存在题目 `SOURCE.md` 的现有分节中。行为依据链接来源，建模选择保存验收对应表，
待定项记录缺口；实现和运行后链接实际代码与原始证据。已有对应表直接补齐，不另建流程文件或状态系统。
每项验收要求均需有对应关系，允许多条要求共用一个用例，也允许一条要求需要多个用例。

| 对应内容 | 需要说清楚什么 |
| --- | --- |
| 要求与依据 | 对应公开条款或可明确推导的规则；区分来源事实、建模选择与未知 |
| 激励与预期 | 连接、初态、输入变化及合法范围；预期波形、数值或性质怎样独立确定 |
| 观测与判定 | 测量量、单位、参考信号或事件、观察区间、汇总方式和通过规则 |
| 公开自测与终评 | 公开代表用例提供什么反馈；终评增加什么条件，每项变化针对什么错误 |
| 正确与错误对照 | 应接受的等价实现；应检出的典型错误，以及违反哪条判据 |

早期允许数值和证据待定，但要先区分“测什么尚未决定”和“量已定义、数值待校准”。
例如输出响应可定义为事件后进入并持续留在误差带内的时间，也可采用其他有依据的定义；
仅写“时间容差 TBD”不能替代选择。定义尚未确定时标明设计缺口，不为完成表格任选一种。
实际评分前，影响正确性的定义、合法范围、门限和容差必须明确并公开。

预期结果来自行为依据、独立计算、可信留出数据或适合该工程任务的性质判定。
gold 用于检查可实现性，并与其他候选接受同一判据；不能直接把 gold 的输出当作唯一答案。
在公开接口和工程限制内，checker 接受不同的内部状态变量和事件组织，不按参考解源码形状判分。

按[公开自测与独立终评的分工](#公开自测与独立终评的分工)选择实验。
要求覆盖一个行为范围的题，终评在公开合法范围内改变波形、初态、事件顺序、参数或实例组合，
针对公开样例的硬编码和遗漏行为增加检查。只验收固定工况的题不擅自扩大范围。
变化项按本题错误机制选择，不默认用 PVT、极端工况或更多随机种子扩充。
真实电路结合题按约定的接口、替换边界和相关电路指标验收，全 VA 题可以直接验收子模块行为；
两者都不为终评增加未声明的电路职责。

两套测试遵守相同的指标定义与容差规则，可以共用判据和测量代码，并分别提供公开、私有用例。
独立终评要求从冻结交付物重新执行，使用可信的固定台架、判据和用例；
不读取求解者留下的 PASS 标记、结果文件或修改过的公开测试副本作为成绩。
共用测量代码也需要独立校准，不能靠公开与终评互相一致证明正确。

观测方案应说明覆盖点或区间、采样或插值方式，以及缺失、非有限值和不完整波形如何处理。
离散采样通过只能说明所测点或已建立误差界的范围，不能直接声称检查了整个连续区间。
时序题按[边界约定](task-package.md#时序边界与验收说明)区分输入斜坡、输出响应、事件参考与观察窗口。
起止点、最短窗口、参数覆盖及多实例事件需要相容；排除事件邻域不能同时删去必需观测并触发缺失失败。
未决条件保留待定，不通过新增无依据的平滑或启动等待来回避冲突。

checker 按[独立判据与校准要求](#独立判据与校准覆盖什么)核对预期、正确实现和错误对照，
并检查冻结交付物收集、终评实际入口和[失败计分及原因](#任务分数与失败原因)。
规则与代码可先设计，实际执行遵守当前授权；数值门限需有依据并经过相应校准。
完成设计意味着覆盖和待定项已能逐条 review；可用于正式评分还需要这些待定项解决，
以及具名版本的实际校准证据，按现有阶段检查推进。

#### 结果呈现

最终报告采用 `Specification | Limit | Value | Pass/Fail`，完整反映所有验收条件。
表格和 JSON 从同一份 checker 结构化结果生成，保留测量范围和对应工作点；
双边范围与组合条件须展示完整，不能只截取一个代表数值。
数值判定使用未舍入的值，展示精度不改变门限；完整性单列，核对规定条件和必要观测是否齐全。
环境导致无法判定时标明原因，不冒充性能失败或通过，按后文环境缺陷规则处理。

测量题的验收表评价测量与报告是否正确。固定 DUT 的性能不达标时，仪器如实报告仍可以满足任务；
DUT 的性能结论与求解者仪器的验收结论分别展示。公开自测与终评遵守相同的指标定义，
公开条件只覆盖明确提供的范围，隐藏条件仍限于公开合同。

### 审核分工与分组交付

人工按[关键原则](design.md#人工如何判断题目质量)判断内容与工程取舍，执行检查与完成条件由
[英文 Agent 流程](agent-workflow.md)规定。工具检查和作者校准不能代替人工设计认可。
内容结论与运行成熟度分别记录，不另建审批队列。功能族 README 保存短的内容结论与待取舍，
当前题包进度由批次 README 维护；运行证据保留在原记录中。

#### 人工介入与批量交付

人工参与集中在批次方向、代表题样板和批量录取。已经确认的范围与决定直接沿用。
以下分工沿用现有题包阶段，不新增审批阶段或逐题过程签字。

| 参与点 | Agent 与工具先完成什么 | 人工判断什么 |
| --- | --- | --- |
| 批次方向 | 整理电路资产、工程动作、任务清单、同源区别、短行为约定及代表题建议 | 哪些工作值得考、题目之间是否有实质区别、建模与适用边界是否合适 |
| 代表题样板 | 形成有依据的 gold、公开自测、终评、评分及 instruction；提供获准执行的校准和模型试跑证据，标出未执行项 | 目标能力是否被正确考察、材料与验收是否公平、实测难度与解题成本是否符合用途；据此确定可复用范围 |
| 批量录取 | 按已定范式逐题生成、检查、修复和校准，给出每题短结论与完整材料链接 | 按题决定录取、修改或暂缓；详细查看代表项、偏离样板的项、异常项及人工选定项 |

gold 实现、预期推导、用例与错误对照展开、checker 编写、题面生成、格式修复和常规调试由 Agent 负责。
数值先由 Agent 查来源、推导或在授权范围内校准。已有明确工程指标直接沿用；
数值误差与观察分辨率需有证据。影响工程含义、合法实现范围或难度的新取舍交人工判断，
不把每个观测点或容差计算都交给人工，也不为让 gold 通过而放宽合同。

中途只提交无法由现有来源和已定规则解决的实质选择，例如来源冲突、新建模假设、
工程指标取舍、任务重复或范围变化。Agent 先给出证据、推荐方案及其影响，合并相关问题。
普通 lint 错误、实现缺陷和可定位的 checker 缺口由 Agent 修复。
执行授权不足或环境受阻时，记录受影响任务和可继续的设计工作；不代改其他组件或扩大实验范围。

人工默认看到一张批次短表，每题一行，包含“题目与新增工作、内容建议、运行事实或缺口、待决问题、材料链接”。
详细规格、预期与用例对应表留在 SOURCE，checker 与校准证据保持原位置，按需展开。
每题仍需完整的 Agent 检查和适用校准；人工选择性深入查看不免除其他题的检查，
也不将一个样板或一次批次方向认可写成所有题已录取。
最终决定按题号和实际版本保留在现有审核记录中，继续由已有 lint 检查阶段与材料，
人工判断与证据真实性不由 lint 代替。

#### 运行事实与交付入口

运行成熟度的具体含义如下。

| 运行环节 | 需要记录的事实 |
| --- | --- |
| 作者执行 | 具名版本的参考实现或电路资产是否实际运行，后端、工具版本、设置与证据是什么。原始资产运行不等于题包运行 |
| 独立验收与校准 | 完整交付和终评是否走通，参考、其他正确实现及典型错误是否得到有效判定，仍缺哪些覆盖或身份核对 |
| Agentic 公开试跑 | Agent 能否自行发起公开测试、获得波形和诊断、修改后重试；时限与调用预算内是否有有效迭代机会，异常和交付如何处理 |

没有执行的环节写未验证；存在缺口时写具体缺口和受影响范围。后端缺陷不证明题目设计差，
题目值得保留也不证明已经具备评测条件。内容认可、历史作者记录、当前题包校准、模型成绩和正式录取继续分别处理。
无模型的工具链检查、参考样板运行和实际模型试跑分别说明；前两者可以验证调用与反馈路径，
不能作为模型完成率或实际解题迭代的证据。

真实电路固定数据建模的数据生成与候选运行依赖不同；固定数据包阶段不开放原电路查询。
在线器件表征或混合工程的迭代依赖器件环境。全 VA 分类也不构成选定后端支持实际任务的证据。
旧批次有 Spectre Agentic 运行记录，只支持当时的题包和协议，不能自动证明新格式已经接通。

人工 review 的统一入口是批次短表和实际题包。中文导读按上述分工说明关键结论与待取舍，
链接完整英文 instruction、独立接口文件、公开 VA 工程及作者证据；实现思路与交付伪代码按需展开。
求解者题包使用英文工程材料，
必要规则应在其公开材料中自足，不能靠中文导读补齐隐含合同。参考解与 checker 留给最终审核。

代表题收口后，其余任务按共用电路资产分组，逐组交付。每组一起说明不同题型的新增工作、
同源区别、内容结论和运行缺口。完成一组就提供该组材料，不等待全部任务结束；已有建设授权继续有效，
不为每组重复申请许可，最终人工审核保留。具体分组以功能族清单为准。

### 按批次管理与逐题录取

2026-10-15 已确认：每批包含实际题包，完整题包按题审核和录取，原批次保留去向与审核记录。
日常草稿建设沿用同一个 benchmark 工作区和分支，用提交记录修改过程，不为每轮讨论或草稿修改新开分支。
草稿保存在 main 不表示已成为正式题目；正式题集由 `benchmark/tasks/benchmark.toml` 和对应审核记录确定。

新工作按电路功能族和小批次组织，例如 `material/draftbench/batches/r01-sampling-01/`。
批次内的 `tasks/<task-id>/` 保存实际题包；共用电路材料仍由 `draftbench/circuits/` 维护。
批次 README 是续聊与人工审核入口，列出本批范围、当前阶段、已认可内容、剩余问题和下一项工作。
题目清单记录 ID、电路功能、工程动作、审核结论、对应版本及实际文件位置。
审核面向题包中的公开材料、参考解、checker 和校准证据，不仅审核选题名称。

代表题合同审核、建设与作者校准、最终人工题目 review 继续按上方流程进行。
一题的完整题包通过本版人工审核后，移动到 `benchmark/tasks/<task-id>/`，更新正式清单与关联索引。
原批次保留审核结论、版本和正式题包链接，不另存一份继续维护的有效题包。
同批需修改或暂缓的题目留在批次内，不阻止其他已通过题目录取；批次不能整体推断为已认可。

录取时更新 `benchmark.toml` 的题目 ID 和顺序，并核对 `defaults.toml`。
只有共用环境设置发生变化时才修改默认配置；题目特有设置放在自己的 `task.toml`。
共用默认配置的修改需要检查对已录取题目的影响，并补做受影响的验证。
正式题包所需的源码和 checker 辅助文件随题保存，不依赖仍在草稿批次中的文件。

当前草稿已分成[三批](../batches/README.md)，共 58 个题包；41 个更早题包与五份旧首批清单保存在[历史题包目录](../../historyref/tasks/README.md)。
登记与索引读取实际批次，历史记录通过路径映射读取原资产，不改写封存身份。

## 解题与最终验收分别执行

主评测采用 [Agentic 评测](../../../../GLOSSARY.md#agentic-评测)，允许 Agent 在约定预算内
读取材料、运行仿真、查看反馈并修改交付物，以任务完成率衡量工程能力。
[One-shot 评测](../../../../GLOSSARY.md#one-shot-评测)作为对照，具体可用材料与交互权限
随实验配置固定，不能把不同权限的结果混为同一条件。

默认向 Agent 提供公开自测，参考答案、终评私有用例及专用评分入口不进入解题环境。
公开主集向研究者提供复验材料，不等于把整个题包交给求解者。
终评在提交后独立执行，不作为该次解题的迭代工具；若完整验收反馈开放给闭环，
必须单列为不同评测配置，不能沿用留出实验的结论。

公开自测保留两种方式：出题者提供固定测试，或在固定工程连接下允许自定义激励与观测。
按工程目标选择并试跑，不统一要求 Agent 自写临时测试台。
各题记录可修改范围与自测方式；固定数据包建模阶段不开放查询原电路。

预算耗尽时验收最后完整保存的候选，不事后挑选历史最好结果。
工具、反馈、墙钟时间、仿真次数及终评资源需要随正式协议固定。
现有[Agentic 试跑协议](../../../../experiments/benchmark_first_batch/agentic/README.md)
属于历史批次设置，不能自动作为后续所有任务的资源合同。

### 公开自测与独立终评的分工

先明确任务承诺哪一种正确性，再设计公开与终评实例：

| 任务合同 | 验收范围与成绩含义 |
| --- | --- |
| 列出的有限工况达标 | 检查全部列明条件；可以公开所有工况或测试，不据此声称范围外也正确 |
| 在输入、参数和历史范围内满足行为 | 公开范围与全部行为要求，用未参与本次闭环的新实例检查遗漏；有限测试仍不证明整个范围 |
| 根据数据预测新实验 | 留出完整实验，按公开误差标准验收；先确认公开数据足以支持所要求的预测 |

数据建模不把同一条波形的相邻点拆成公开与留出数据来证明泛化。
固定工况题也不能为了增加隐藏测试，加入题面已排除的条件。

| 材料或执行 | 责任与输出 |
| --- | --- |
| 公开 Spec | 说明全部行为要求、合法范围、测量定义、容差、交付限制和计分规则 |
| 作者提供的公开自测 | 用代表实验诊断主要语义，给出实际值、预期值或允许范围、误差位置及通过结论 |
| Agent 补充的自测 | 在题目允许的文件与工具范围内验证假设；质量由求解者负责，其结论不作为评分输入 |
| 独立终评 | 从冻结提交重新执行作者控制的验收，复验公开代表条件并覆盖全部必需验收要求；范围型任务另含未参与闭环的实例 |

不按固定百分比划分公开与私有用例，也不把规格语义本身分成公开与隐藏两组。
公开自测应支持有效调试；若任务还要考察测试设计，明确给定工具和工作范围，
不能把缺少调试入口默认解释为题目难度。两套实验可以共用 TB 模板、测量和判定代码，
不要求维护两份不同的 checker；公开与终评必须遵守相同的指标定义和容差。

独立执行与留出验证解决不同问题。重新执行可信评分程序防止候选用自报结果替代验收，
这在完整 TB 公开时也能做到。留出实例用于观察未参与调试的条件。
评分工况可以全部写入 Spec，但若 Agent 重建了等价 TB 并取得同样可靠的反馈，
未提供评分文件本身就不构成测试信息的隔离。允许范围内的充分自测是正常工程行为，
不能将针对全部声明条件完成实现视为利用漏洞；应修补的是违反规格却仍能得分的测量或覆盖缺口。

正式实验前固定终评实例、生成规则、随机种子和评分版本，同题各参评提交使用同一协议。
终评补漏后登记新版本并重新校准，对需要比较的冻结提交按同一版本重新评分；
若修正影响了解题反馈，按[环境缺陷规则](#环境缺陷怎样影响成绩)重跑解题过程。

### 有限采集建模示例

[有限采集题](../batches/r01-sampling-01/tasks/r01-spec-acquisition/instruction.md)
要求在公开输入、参数和控制历史范围内实现连续状态。下表说明分工，是设计示例，
不表示题包已实现这些测试或已完成校准。当前合同草稿中的 2 mV 是对规定响应的实现误差，
不是窗口结束时输出与输入的差；其数值可行性仍待作者校准。

| 规格语义 | 公开自测提供的代表实验 | 终评增加的条件 | 主要错误对照 |
| --- | --- | --- | --- |
| 从 `vinit` 启动 | 四种初始控制组合，含非默认初值 | 换输入、初值与采集时间常数 | 从直流稳态开始；只支持保持启动 |
| 有限且依赖输入的采集 | 不同输入电平，短窗与长窗 | 新的电平、窗长和参数组合 | 瞬时采样；固定时间常数 |
| 采集中持续使用瞬时输入 | 窗内改变输入 | 多次变化，改变时刻和斜率 | 只读起始输入；不更新输入相关时间常数 |
| 前拍状态继承 | 连续短窗，中间改变输入 | 不规则短长窗及多周期历史 | 每窗重新初始化；只在窗末更新 |
| 保持状态不变 | 保持中改变输入，含长保持 | 不同保持值、时长与输入序列 | 漏电；输入穿透 |
| 有限复位、优先级与恢复 | 短复位，分别释放到采集与保持 | 改变初始偏差及控制重叠顺序 | 瞬时复位；采集优先；释放时清除残余 |
| 模式切换连续 | 检查公开实验的切换邻域 | 在不同历史状态下切换 | 输出跳变；额外延迟或平滑 |

所有实验都按同一方程和误差规则检查轨迹，不能只比较窗口末值或平台。
恒定输入片段可用解析响应，变化输入片段需独立求解；
控制阈值附近的采样、插值和数值误差按[观测方案](#逐题-checker-与终评设计)校准。
终评只改变题面允许变化的参数，不擅自扫描其余固定默认参数。
公开阶段的固定预期轨迹和误差分析可以帮助调试，无需向求解者提供参考 VA 实现。
例如“短采集、保持、短复位、恢复采集”的新组合检验状态继承，不引入新机制。

## 每题固定后端，设计时处理能力差异

每题固定解题和评分使用的仿真后端、工具链版本及数值设置。
同题比较不同模型时保持相同环境，Agent 不自行选择或切换仿真器。
不同题因能力需求可使用 EVAS、ngspice、Spectre 或经过验证的其他工具链。
同题更换后端属于不同实验配置，需要声明并按需校准。

处于已验证 ngspice 支持范围、且有可信独立 checker 的完整任务，可以由 ngspice
独立给出正式成绩，不强制经过 Spectre。跨后端校准按任务风险和证据缺口选择。
采用 Spectre 验收的题仍执行声明的协议，EVAS 通过不能直接替代。
这项 benchmark 政策不改变 EVAS 开发自身的 Spectre 行为对照要求。

后端语言限制由出题者在选型、设计和校准时处理，不作为题面中额外的语言子集限制。
工具链配置和版本仍须记录。参考解能运行不足以证明环境适用，校准要覆盖
有代表性的不同正确实现及典型错误。

符合题意且 VA 用法正确的候选，若因后端能力不足无法执行或被错误执行，应归为环境缺陷。
环境缺陷不证明候选满足规格，也不自动判为通过。保留候选、失败和诊断证据，
不能仅凭非零退出码或超时认定候选错误。

属于[当前建模范围](design.md#当前采用哪些边界为什么)且具备可信环境的题，
可以在 EVAS 尚不支持时继续建设。相关支持需求由 EVAS 另行处理，不能由有限样本
推导任意提交或整个题库均能开源复现。

## 独立判据与校准覆盖什么

题面公开行为目标、指标定义、误差标准及工程限制。隐藏测试仅检查公开合同中的要求。
算法、诊断顺序和实验选择尽量交给 Agent；必要过程约束须明示。

判据应来自公开合同、独立推导、独立波形分析，或数据建模的可信留出实验。
参考解用于验证题目可完成，不替代正确性定义。
系统题同时验收规定职责和交互，测量题核对测量数值，性质检查题校准误报、漏报与时机。
各类具体边界见[任务定义](task-types.md)。

校准分别检查预期、候选分类和实际执行：

| 校准对象 | 需要取得的证据 |
| --- | --- |
| 真值与测量 | 手算例、解析解或可信独立数据能核对预期；覆盖测量窗口、采样、插值及数值误差预算 |
| 正确候选 | 参考解和有代表性的其他正确实现被接受，不限制为参考源码的状态表示或事件组织 |
| 错误候选 | 典型错误完成测量后因对应规格违例被拒绝，记录触发它的实验和判据 |
| 完整性与执行 | 缺测量、非有限值、不完整轨迹不会被当成通过；冻结交付物经真实终评入口得到规定分数与原因 |

例如有限采集题要检出瞬时采样、每窗清零、固定时间常数、瞬时复位和保持漏电。
这些错误因编译或后端失败而得 0 分，不证明数值 checker 已检出相应语义。
共享代码的两套测试互相一致，也不代替上述独立证据。
容差须先有用途或建模依据，再验证真值与测量误差是否足够小；不能仅按参考解的误差反推通过门限。
试跑后继续核对实际模型提交，补齐发现的误收和误拒。
保存源码、输入、初态、checker、工具链及数值配置的身份。
规格、预期答案、参考解、评分或相关运行设置改变时，重做受影响校准并登记新身份。
有限校准只证明已测范围，不保证所有可能实现。

## 任务分数与失败原因

主成绩使用任务级 0/1：冻结提交满足全部必需验收要求记 1，已执行但未完成任务记 0。
逐项测量、误差和语义通过情况用于诊断，不按 TB 数量或正确采样点比例分配主分。
拆分同一实验、增加重复用例或延长正确的保持段，不应改变要求的评分权重。
例如有限采集题若复位错误，即使绝大多数采样点正确，任务仍未完成。

只有公开合同本身包含优化目标时，才另行定义连续指标或辅助分数，
明确功能前提、计算方式及归一化规则；普通规格实现题不额外奖励超过要求的精度。
这类指标与任务完成分分别报告，不能用优化收益抵消必需功能失败。
汇总报告任务完成率并按任务类型和功能族展示，保留题集、分母、预算与版本；
未执行项明确列出，不把部分运行结果写成完整题集成绩，也不选择性删除失败尝试。

2026-10-20 人工确认：任务评测成功按公开合同计分；已执行的失败尝试计 0 分，失败原因单独记录。
提交非法、编译失败、运行失败、超时、波形缺失和数值超差不能仅因诊断类别不同而漏写失败分数。
后端或基础设施造成的失败也保留该次尝试的 0 分及原因，不能据这个分数认定候选的 VA 行为错误。
尚未执行、仍在运行或设计材料待定没有已完成成绩，不能为了补齐记录而编造 0 分。

复用现有报告的状态、诊断和日志字段，不另建评分状态系统。交付检查应同时核对失败分数确为 0、
原因及原始诊断可追溯；只看退出码、错误名称或 reward 文件是否存在，都不足以确认最终计分。
公开反馈可以继续区分预检、数值和执行错误，终评记录则须落实上述分数约定。

作者校准另看检出证据：错误模型只有完成测量并违反独立判据，才算语义检出；
因编译、超时或后端能力不足得到 0 分，不算已证明该错误被数值 checker 检出。
正确 gold 因运行问题得到 0 分，同样不能据此认定题目已经校准。历史回执保留原分数和状态，
不得把旧的未评分记录改写为按本约定执行过；后续同步题面、评分入口及运行器后核验新记录。

## 环境缺陷怎样影响成绩

环境缺陷若影响 Agent 收到的解题反馈，修复后在修正且固定的环境中重跑该题各参评模型。
若只影响提交后的独立评分，未影响解题反馈，则对冻结候选重新评分。
旧记录保留，并关联修复后的实验配置；失败和未知尝试不为提高成绩而从记录中移除。
按[分数与原因约定](#任务分数与失败原因)保留失败尝试的 0 分和诊断，尚未执行的检查继续待定。
一般基础设施故障优先恢复原作业，恢复和重试的身份留在记录中；若故障已经影响了反馈，
则适用前述重跑规则。修复后的结果另记，不能覆盖旧失败或把运行失败当作语义检出。

benchmark 负责题目判据与校准，circuit harness 负责共享执行、错误状态和证据收集。
[circuit-harness #5](https://github.com/BucketSran/circuit-harness/issues/5)跟进可靠性改进，
该 issue 存在不表示所有改进已经实现。

## 开源复现保留同一道题的要求

[开源复现](../../../../GLOSSARY.md#开源复现)首先指重新验收已保存的同一候选：
使用规定输入、初态与独立判据，不依赖商业工具复核通过或失败。
重新调用模型生成交付物属于另一项实验。

若替换后端，须在声明范围内验证判分对应关系。不同后端不要求每个采样点完全相同，
但要满足同一行为合同与误差限制。替代后端复验需要对参考解、错误版本和实际提交
进行判分对照，不能只验证参考解。

优先寻找真实电路与配套 VA 模型。用 VA 替代固定器件环境时，保持候选代码与接口、
公开行为要求和验收标准，并保留影响判定的电路效应，校准替代环境。
无需复制全部晶体管内部状态；删减题目要求得到的版本另记为简化变体，不能证明原题已可复现。

正式发布分别报告以下两集的题数、成绩、工具版本与复现范围：

| 集合 | 资格 |
| --- | --- |
| 公开主集 | 不依赖商业工具即可重新验收，有开源工具链和独立 checker 的校准证据 |
| Spectre 扩展集 | 完整验收仍依赖 Spectre，发布可分发的任务、判据及运行说明，并声明商业依赖 |

直接使用 ngspice 正式评分的题不统一要求 Spectre 对照。
集合归属随版本固定，补齐环境与校准后才在后续版本调整。
来源、许可与对外材料遵循[使用约定](../../historyref/README.md#使用约定)。

工具依赖分组参考 CVDP 官方 `commercial` 与 `no_commercial` 发布方式，见
[数据说明](https://huggingface.co/datasets/nvidia/cvdp-benchmark-dataset/blob/main/README.md)。
[CVDP 论文](https://arxiv.org/html/2506.14074v1#S3)说明部分验证任务依赖商业工具；
本项目的后端选择与判分对应关系仍需自身校准。

## 分析成绩时保留工程差异

报告任务完成率，同时呈现任务数、来源分组和工程工作覆盖，考虑同源任务的相关性。
普通参数变体作为条件，不重复增加任务数。不按文件数、代码长度或预估难度加权，
完整仓库任务可单列表现，工作量不直接折算为更高分值。
具体汇总口径、正式交互预算和五类题量仍需代表题研究及试跑后确定。
历史批次的分类、分母和运行身份保持原记录，不重命名为新五类成绩。

## 共享评分程序

本节保留旧批次的建设与恢复方式。新题 checker 的唯一维护与执行入口在各题 `tests/` 内，
复用逻辑也随题保存并校准，不把历史共享源码作为正式题依赖。
以下生成器用于恢复历史题包或维护指定草稿批次；它们不能直接向 `benchmark/tasks/` 录取题目。

[checkers/spectre_waveform.py](../../historyref/legacy-authoring/checkers/spectre_waveform.py) 是六题共用的评分源码。
[任务生成器](../../../../experiments/va_screen/build_tasks.py)将它复制到每题的 `tests/verify.py`；
任务运行时执行该副本，`tests/cases.json` 保存各题的网表、独立期望值与容差。

恢复或修订旧批次的共享源后，需要同步受影响的执行副本，并重做其参考解和错误版本校准。
生成器会重建全部六题文件，运行前应保留正在修改的任务。提交前使用
[身份检查](../../../../experiments/va_screen/README.md#身份与再校准)确认源、副本及校准记录一致。
校准通过证明这些已测条件，不能证明评分程序覆盖任意错误实现。

[checkers/triangle_oscillator.py](../../historyref/legacy-authoring/checkers/triangle_oscillator.py) 单独负责振荡器修复题。
它使用正速度的分段解析积分和三角波折返关系；固定题目配置与错误版本校准见
[来源和验证边界](../../historyref/tasks/va07-triangle-repair/SOURCE.md)。无需 Spectre 的检查器回归：

```sh
python3 -B -m unittest discover -s experiments/backends/dvs2-spectre-validation -p test_triangle_oscillator.py -v
```

旧 va07 资产的 EVAS 接入入口是 [triangle_evas.py](../../historyref/legacy-authoring/checkers/triangle_evas.py)，
通过操作者指定的 circuit harness 执行，仅覆盖 `constant-tighter` 开发配置。
[调用方式、配置映射与未完成的负例验收](../../historyref/tasks/va07-triangle-repair/SOURCE.md#local-evas)
由该任务维护。原解析判据与 case 文件字节保持不变。当前 Spectre 入口经由共享的
`circuit_task` 执行，旧校准与当前入口的复核证据分别记录。

## 环境与结果

每个任务在自己的 `environment/` 中声明运行环境。
现有远端 Spectre 题使用固定 digest 的 Python 基础镜像与远端 verifier；
这些任务镜像本身不包含商业仿真器，运行时按各题所属批次的说明指定 verifier。
这不是后续所有题的统一后端要求，后端选择遵循前面的固定后端原则。
镜像应记录依赖版本和构建方法；执行记录应保存实际使用的镜像身份。
完整运行日志与临时输出放在 Git 忽略的 `runs/` 中。

Benchmark 评分与 [EVAS 正确性验证](../../../../evas/validation/README.md)分别维护和报告。
EVAS 的构建与运行方法见 [仿真器说明](../../../../evas/README.md)。
