# 怎样使用全量审核草稿

这轮用 GLM 5.3 按400家族审1200个任务包，目的在于整理后续讨论的候选与问题。
模型完成报告只表示有一份待复核意见，不能据此把题目移入正式评测集。

## 试审已经暴露的限制

第一版试审001、024、102、249。001与024的文件路径校验失败，102与249产生结构合格草稿。
001第一份报告把题目名称及可追踪的事件逻辑直接当成真实BBPD架构依据，并推及环路性能。
这项判断不成立：原题没有给出retimed_data的来源，不能由任意三路输入的真值表证明实际早晚判相。
题目名称真实、模块规则能验收、规则代表真实电路，是三个需要分别核对的判断。

第二版已要求单列架构依据。001的重审正确指出了retimed_data来自独立激励、闭环连接与控制极性缺失，
但仍把组件判为 `supported_in_assets`。因此自动架构标签不宜用作准入筛选。
主代理对这个已知样本仍保留“早晚判相依据未证实”的结论，详见 [Alexander 学习说明](alexander-bbpd.md)。
这个试审限制随全量结果一并保留，不因增加并发而消失。

路径拼写只允许做确定性修正：规范化 `..`，或在同一任务包内匹配唯一文件名。
修正原文及规则保留在 `path-corrections.json`；不能自动改证据行号，更不能把引用存在当成论点成立。
历史 provenance 与当前 r53 的 seed 不同，也可能是版本策略变更，须先看当前 score_policy 和实际字节。

## 从意见到题卡

1. 按具体工程用途筛选，回到输入、状态、采样和输出的关系。涉及电路性能、闭环或架构的论断，补查主源及真实工程。
2. 对高影响发现读原文件并构造反例。区分确定冲突、未公开行为、环境限制，以及旧版本与新版本的不同。
3. 把DUT、修复和测试的保留建议分开讨论。同一电路无需三形态都保留，迁移建议也不要求凑齐五类。
4. 初步接受方向后再补规格与独立checker；按实际需要选固定后端，进行健康实现、负例和边界条件校准。

本轮任务包输入保留全部VA源码，重复网表行和JSON值以带原位置的引用表示。
原始r2的最大输入049被CLI明确拒绝为 `Prompt is too long`；r3改为按JSON字段值去重，
保留失败响应和版本区别。静态还原校验检查原始文件哈希、引用内容及三形态分母；这不代替模型内容复核。

运行入口、实际覆盖和未完成项见 [迁移主页](README.md#全量审核完成与阶段记录)，
大体积原响应仅在本地ignored `runs/`，不作为已发布资产。

## 新增的测试台选题审查视角

2026-10-10，全量静态审核运行期间，讨论补充了 VA 测试模块的工程价值判断。用户随后明确：随电路运行直接报告指标与结论、省去单独导出和 Python 后处理，本身就是成立的用途，不能因离线可实现而排除或自动降级。统筹复核旧 Testbench 时，补查其测量条件、事件历史、异常处理、报告和端口集成；需要时再考察协议交互和响应驱动的激励。固定激励的测量或检查可以成为正式题，复杂度另评。具体区分见[讨论稿](../DISCUSSION.md#va-测试台相对离线分析增加了什么)。

这项视角是后续人工统筹与补审的标准，不声称当前400家族的原始GLM请求已系统覆盖它，也不在运行中改写已有prompt或报告。VA工程关联度较低不等于算法简单，基础题仍可保留；不为了显得困难而给旧题强加无实际用途的交互。
